# 页面洞察增强设计

## 背景

NEC 文档站点同时存在几类页面：

- 超长教程页，如 `ai-tools/isaac-gym-rl-tutorial.mdx`
- 正常长度的指南页，如 `community/about.mdx`
- 导览索引页，如 `training/index.mdx`
- 极短资料页、占位页或组件页，如 `community/maintainers.mdx`、`snippets/snippet-intro.mdx`

当前站点缺少统一的页内洞察信息。用户希望：

1. 检查哪些页面加载可能过长、哪些页面过短
2. 为正文型文档统一加入 AI 总结
3. 为正文型文档统一加入阅读时间估算，如“预计阅读 6 分钟”

本设计目标是提供一个稳定、可维护、构建期静态生成的方案，而不是依赖运行时模型或人工逐页维护。

## 目标

### 主要目标

- 为正文型文档统一显示 `AI 总结 + 预计阅读 X 分钟`
- 自动识别超长页与超短页，便于后续内容治理
- 尽量不污染原始 `.mdx` 内容
- 允许少数重点页进行人工覆盖

### 非目标

- 不对首页、索引页、纯导览页、组件页强制显示摘要
- 不在运行时调用外部 LLM
- 不在第一版中自动拆分超长页面
- 不要求作者为每个页面手写摘要

## 范围

### 包含范围

- 站内正文型 `.mdx` 文档
- 构建前页面扫描、分类、阅读时间估算与摘要生成
- 页面顶部统一渲染洞察信息
- 超长页 / 超短页报告输出

### 排除范围

- 首页和明显落地页
- 索引、总览、导航、资源聚合类页面
- `snippets/` 等非正文内容目录
- 仅嵌入组件、占位或极薄内容页

## 方案对比

### 方案 A：直接改每个 MDX

通过脚本把摘要和阅读时间直接写回所有正文页顶部。

优点：

- 实现路径直观
- 页面渲染阶段不需要额外读取元数据

缺点：

- 会批量修改大量内容文件
- 后续正文更新后，摘要容易漂移
- 难以区分自动生成内容与作者原文

### 方案 B：生成元数据并统一渲染

构建前扫描页面，生成独立元数据文件；页面统一读取元数据并渲染。

优点：

- 页面源码保持干净
- 便于统一样式与规则迭代
- 便于输出超长 / 超短分析报告
- 便于后续加入人工覆盖

缺点：

- 需要额外确定稳定的挂载方式

### 方案 C：只做离线分析

先生成长短页报告，再人工挑选页面补摘要。

优点：

- 风险最低

缺点：

- 无法满足“全站自动显示”的目标

### 结论

采用方案 B：`生成元数据并统一渲染`。

## 总体设计

方案拆为两层：

1. 页面分类层：先判断页面是否属于正文型文档
2. 正文增强层：仅对正文页生成并展示摘要与阅读时间

这使系统能同时处理长教程、短资料卡、导览页和落地页，而不依赖单一规则如 `index.mdx`、`toc: false` 或原始行数。

## 页面分类规则

页面不采用硬编码单条件判断，而采用信号打分与人工覆盖并存的分类方式。

### 分类结果

- `article`：正文型文档，显示 AI 总结与阅读时间
- `index`：索引 / 总览 / 导览页，不显示
- `landing`：首页 / 落地页，不显示
- `stub`：极短资料页、占位页或薄内容页，不显示

### 正文加分信号

- 有连续自然段文本
- 有 2 个及以上正文标题
- 纯文本提取后字数达到最低正文阈值
- 段落主体不是由卡片、导航链接或表格构成

### 导览减分信号

- `CardGroup`、`AccordionGroup`、大段链接列表占比很高
- 文件名为 `index.mdx`
- 标题或路径包含“总览”“索引”“资源”“导览”“学习地图”“首页”等特征词
- 页面主要作用是跳转而不是承载说明正文

### 强制排除

- 根首页 `index.mdx`
- `snippets/` 等非内容目录
- 明显仅用于组件挂载、占位或嵌入的页面

### 设计原因

站内存在如下反例，说明不能靠单一字段粗暴判定：

- `community/about.mdx` 有 `toc: false`，但它是正文页
- `training/index.mdx` 虽然有实质信息，但主要承担集训导览功能，整体更适合归为导览页

## 长度分层与异常页识别

虽然所有正文页都会显示阅读时间与摘要，但仍保留超长 / 超短标记，便于后续站点治理。

### 判定口径

长度与阅读时间不按原始文件行数计算，而按清洗后的正文内容计算，避免被以下内容放大或干扰：

- `import` 行与 MDX 组件标签
- 大段代码块
- 导航卡片
- 图片 `alt`
- 重型表格噪音

### 建议阈值

- `short`
  - 正文内容少于 250 汉字等效，或阅读时间小于等于 1 分钟
- `normal`
  - 正文内容约 250 至 4500 汉字等效，或阅读时间 1 至 15 分钟
- `long`
  - 正文内容超过 4500 汉字等效，或阅读时间大于等于 15 分钟

### 用途

- `short`：提示页面可能过薄，适合作为索引或补充说明
- `long`：提示页面较长，建议先看摘要并按目录阅读

## 阅读时间算法

阅读时间基于“可读正文”估算，而不是简单按全文字符数除法。

### 预处理

扫描器需要提取并分别统计：

- 正文文本字符
- 英文单词数
- 代码块内容
- 表格内容
- 标题层级与段落数量

### 折算建议

- 中文正文：300 字 / 分钟
- 英文正文：180 词 / 分钟
- 代码块：按正文 20% 权重计入
- 表格：按正文 50% 权重计入

### 输出规则

- 结果向上取整
- 最小显示值为 `1 分钟`
- 输出格式统一为 `预计阅读 X 分钟`

## 摘要生成策略

摘要在构建前离线生成，不依赖运行时外部模型。

### 第一版策略

采用稳定的抽取式摘要：

- 利用页面标题
- 利用前两段正文
- 利用二级标题
- 利用结尾总结段

再组合压缩为 2 至 4 句摘要。

### 这样设计的原因

- 不依赖在线模型、API 配额或网络状态
- 结果可重复、可调试
- 更适合文档站持续集成

### 后续可升级点

后续可选接入更自然的 LLM 改写层，但不改变当前元数据与挂载结构。

## 数据结构设计

### 自动生成文件

新增文件：

- `generated/page-insights.json`

每条记录示例：

```json
{
  "slug": "mechanical/chassis",
  "filePath": "mechanical/chassis.mdx",
  "pageKind": "article",
  "readingMinutes": 6,
  "lengthBand": "normal",
  "summary": "介绍底盘设计的基本分类、常见结构和选型思路，帮助新成员建立对移动机构的整体认识。",
  "stats": {
    "textChars": 1680,
    "englishWords": 34,
    "codeWeight": 42,
    "tableWeight": 90,
    "headingCount": 7,
    "paragraphCount": 11
  },
  "signals": {
    "positive": [
      "has_multiple_headings",
      "has_continuous_paragraphs"
    ],
    "negative": []
  }
}
```

### 人工覆盖文件

新增文件：

- `generated/page-insights.overrides.json`

允许对少数页面进行人工控制：

- 自定义 `summary`
- 强制改 `pageKind`
- 隐藏阅读时间
- 隐藏摘要

优先级为：

`overrides > generated`

## 生成流程

建议新增构建前脚本，例如：

- `tools/ci/generate_page_insights.py`

### 执行流程

1. 递归扫描全部 `.mdx`
2. 跳过排除目录与明显非正文文件
3. 解析 frontmatter 与正文
4. 提取纯文本、代码块、表格、标题等信号
5. 判定 `pageKind`
6. 对 `article` 计算 `readingMinutes`
7. 对 `article` 生成 `summary`
8. 输出 `page-insights.json`
9. 同时输出超长 / 超短分析报告

### 报告输出

建议同时输出一个便于人工治理的报告文件，例如：

- `generated/page-insights-report.md`

报告包含：

- 超长页列表
- 超短页列表
- 被判为 `index` / `landing` / `stub` 的页面及理由
- 可能的误判候选

## 页面挂载设计

### 展示位置

统一显示在正文型文档的页首标题下方。

### 呈现内容

- 一行 meta：`预计阅读 X 分钟`
- 一段摘要：2 至 4 句
- `long` 页附加轻提示：`本文较长，建议先看摘要再按目录阅读`
- `short` 页附加轻提示：`本文内容较短，适合作为索引或补充说明`

### 组件设计

新增片段组件，例如：

- `snippets/page-insights.jsx`

组件职责：

- 根据当前页面 slug 读取 `page-insights.json`
- 读取人工覆盖配置
- 若 `pageKind !== article` 则不渲染
- 若为 `article` 则渲染页首洞察信息

### 挂载策略

第一优先级：寻找 Mintlify 可复用的统一挂载点，实现“全站自动注入”

如果 Mintlify 不支持稳定的全局标题下注入，则采用回退方案：

- 使用脚本为全部 `article` 页面批量插入统一 snippet 挂载
- 仍然保持摘要内容存放在独立 JSON 中
- 不把摘要正文直接写入页面

## 样式设计

样式应延续站点当前暗色视觉体系，强调克制与可读性，不做重卡片化。

建议新增一个轻量信息块，包含：

- 小字号 meta 行
- 正文摘要段
- 极浅边框或背景分层

避免：

- 大面积高对比色块
- 抢占首屏的超大组件
- 与 Hero、CardGroup 风格混淆

## 风险与回退

### 风险 1：正文页误判

缓解方式：

- 记录 `signals`
- 输出报告供人工审查
- 支持 `overrides`

### 风险 2：摘要质量一般

缓解方式：

- 第一版先追求稳定
- 允许对重点页进行人工覆盖
- 后续可升级摘要算法

### 风险 3：Mintlify 缺少稳定全局挂载点

缓解方式：

- 优先尝试统一挂载
- 若不稳定，则回退为批量插入 snippet

## 验收标准

- 正文型页面顶部显示 `AI 总结 + 预计阅读 X 分钟`
- 首页、索引页、纯导览页、组件页不显示该模块
- 生成脚本可重复执行，结果稳定
- 支持人工覆盖少数页面
- 能输出超长页与超短页报告
- 不要求逐页人工编辑摘要

## 实施建议

推荐按以下顺序推进：

1. 先做页面扫描与分类
2. 再做阅读时间估算
3. 再做摘要生成
4. 再做 JSON 输出与覆盖机制
5. 最后接入统一挂载与样式

这样可以先验证“判定是否准确”，再进入页面展示层，降低回滚成本。
