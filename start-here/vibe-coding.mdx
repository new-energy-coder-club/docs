## Loop 流程 —— 写给未来的 FDE 工程师 / AI 实习生

不管任何 CLI 或 IDE，人类都需要对产出物以及上下文有着某一方向的掌控力。

至少在以下方面之一有所基础：

1. 主视觉
2. 代码框架
3. 需求实现 **技术逻辑**
4. 对标竞品和差异

## FDE 框架与协作逻辑

协作逻辑，这里不仅需要成熟的 GitHub 和 Gitee 等 Git 版本管理软件的基础，以及人和机器都看得懂的 Markdown 标记性文本的基础，协作的内容和信息同步形式有着重要的意义。

### 这里有几个原则

- 未来的文档 Readme 不仅是写给人看的，还是写给 AI 看的
- 提示词的质量和框架模板仓的质量，直接决定了产物质量

### 现代 FDE 开发逻辑

- **Spec kit** 细分需求，给出明确的 PRD，并人工 Review 之后，再来相关协作开发
- 认知上的敏锐，来自经验和长期人工 Review 的结果，AI 并不能很好地 Review
- 可以通过 **superpower** 之类的标准开发来处理相关

## 🗼 Kimi Code 实验性功能：/tower

**多个 agent 同时维护 1 个 repo，互不"打架"。**

### 怎么理解

> 想象一下 PM 找不同的人沟通事情。沟通时间、冲突情况都是不保证的，但沟通内容都是 team 内的事情。
>
> 内部有个塔台（tower）来分发任务、协调冲突、指定 reviewer、合并代码、清理残留。

### 更多介绍

- 知乎文章：[Vibe Coding 与多 agent 协作](https://zhuanlan.zhihu.com/p/2068765717583992104)
- 求体验求拍砖，PR 在这 👉：[MoonshotAI/kimi-code#2633](https://github.com/MoonshotAI/kimi-code/pull/2633)

### 如何体验

**（1）安装运行**

```bash
pnpm dlx https://pkg.pr.new/@moonshot-ai/kimi-code@6275c7c
```

**（2）然后：**

- `/tower` 命令 1
- `/tower` 命令 2
- …
- 并发即为上限
